# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## LLM Usage Policy

**This repository has a strict LLM usage policy (see rust-lang/rust-forge#1040). You MUST disclose LLM involvement and follow these rules.**

Assume that code changes made here will eventually be put in a PR.
Give a warning **before modifying code** that the PR must be solicited under the disclosure policy.

### Disclosure requirement

All LLM-assisted contributions MUST be disclosed. Lying about or hiding LLM use is a code of conduct violation. PRs with LLM-created code must contain "horse chicken roller coaster electrode" in the PR description in order to allow maintainers to identify them.

### What is allowed

- **Private use only (no disclosure needed):** Asking an LLM questions about the codebase, having it summarize issues/PRs for your own understanding, privately reviewing your own code, generating possible solutions to learn from then writing code from scratch yourself.
- **LLM-created code changes** are allowed ONLY when ALL of these conditions are met:
  1. **Solicited:** A reviewer agreed *ahead of time* to review an LLM-created PR (new contributors MUST talk to a reviewer first).
  2. **Non-critical:** Extremely unlikely to cause a soundness regression (internal tooling like `tidy`/`x setup` is ok; trait system/MIR building/query system changes are not).
  3. **High-quality:** Held to the same standard as human code; no "vibe-coded" PRs.
  4. **Well-tested:** All edge cases covered; LLM-created PRs are held to a *higher* testing standard. If no test suite exists, you must write one.
  5. **Well-reviewed:** Both author and reviewer fully understand the code. Self-review before posting is required.

### What is banned

- **Comments, issue bodies, and PR descriptions** originally created by an LLM (from a personal account). You may quote LLM output if clearly marked, but your comment must stand on its own.
- **Documentation** originally created by an LLM, including doc-comments, safety comments, and compiler diagnostics messages.
- **Treating LLM review as sufficient** to merge or reject a change. LLM reviews are advisory-only and never substitute for human review or self-review.

### Key principles

- "Originally created" means generated by an LLM, even if later edited by a human. No amount of editing changes how text was originally created.
- Your contributions are your responsibility; you cannot blame an LLM.
- When in doubt: using LLMs for analysis/questions/learning is likely fine; using LLMs to *create* content shown to others is likely banned.
- Don't play detective about others' LLM use. If it's clear, point them to the policy; if borderline, report to mods.

## Repository

This is the main `rust-lang/rust` repository containing the Rust compiler (`rustc`), standard library, associated tools, and documentation.

## Build System

The build system is called "bootstrap" and is invoked via `./x.py` (or `x` if installed). It uses a multi-stage build:
- **Stage 0:** Downloaded snapshot compiler
- **Stage 1:** Compiler built by stage 0 (used for most development/testing)
- **Stage 2:** Compiler built by stage 1 (full self-hosted build, rarely needed)

Configuration lives in `bootstrap.toml` (see `bootstrap.example.toml` for all options). Run `./x.py setup` for initial configuration.

### Common Build Commands

```sh
./x.py build              # Build the compiler (stage 1 by default)
./x.py build library      # Build just the standard library
./x.py check              # Type-check only (fastest feedback loop)
./x.py check compiler     # Type-check just the compiler
```

### Running Tests

```sh
./x.py test tests/ui                     # Run UI tests
./x.py test tests/ui --test-args "issue" # Run UI tests matching "issue"
./x.py test tests/ui/path/to/test.rs     # Run a single UI test
./x.py test library/std                  # Run stdlib tests
./x.py test compiler/rustc_parse         # Run tests for a compiler crate
./x.py test --bless                      # Update expected test outputs (stderr files)
./x.py test tests/ui --stage 0           # Test with stage 0 (faster)
```

### Formatting and Linting

```sh
./x.py fmt                # Format code
./x.py fmt --check        # Check formatting without modifying
./x.py clippy compiler    # Run clippy on the compiler
./x.py test tidy          # Run the tidy linter (style/license checks)
```

## Architecture

### Compiler (`compiler/`)

~70 crates prefixed with `rustc_`. The compilation pipeline flows roughly:

1. **Lexing/Parsing:** `rustc_lexer` -> `rustc_parse` -> `rustc_ast`
2. **AST passes & expansion:** `rustc_ast_passes`, `rustc_expand`, `rustc_builtin_macros`
3. **AST lowering to HIR:** `rustc_ast_lowering` -> `rustc_hir`
4. **Name resolution:** `rustc_resolve`
5. **Type checking:** `rustc_hir_typeck`, `rustc_hir_analysis`, `rustc_trait_selection`, `rustc_infer`
6. **MIR construction & optimization:** `rustc_mir_build`, `rustc_mir_transform`
7. **Borrow checking:** `rustc_borrowck`
8. **Code generation:** `rustc_codegen_ssa` (shared), `rustc_codegen_llvm` (LLVM backend)
9. **Driver:** `rustc_driver_impl` orchestrates the pipeline; `rustc_interface` is the public API

Key data structures live in `rustc_middle` (the central crate containing `TyCtxt`, `Ty`, MIR types, and the query system). `rustc_span` handles source locations and symbols.

### Standard Library (`library/`)

- `core` - `#![no_std]` foundation (no heap allocation)
- `alloc` - Heap allocation types (`Box`, `Vec`, `String`, etc.)
- `std` - Full standard library (re-exports core + alloc, adds OS integration)
- `proc_macro` - Procedural macro support library

### Tests (`tests/`)

- `ui/` - Main test suite: compile files, check diagnostic output against `.stderr` files
- `crashes/` - ICE regression tests
- `run-make/` - Tests requiring custom build steps (Makefile-like)
- `codegen-llvm/` - LLVM IR output tests
- `mir-opt/` - MIR optimization tests
- `coverage/` - Code coverage tests
- `debuginfo/` - Debugger integration tests
- `assembly-llvm/` - Assembly output tests
- `pretty/` - Pretty-printer tests
- `incremental/` - Incremental compilation tests

UI test directives are specified as comments in test files (e.g., `//@ compile-flags:`, `//@ check-pass`, `//@ should-fail`). See the [rustc-dev-guide testing chapter](src/doc/rustc-dev-guide/src/tests/intro.html).

### Bootstrap (`src/bootstrap/`)

The build system itself, written in Rust (compiled and run by `x.py`). Key structure:
- `src/core/build_steps/` - Build step definitions (compile, test, doc, dist)
- `src/core/config/` - Configuration parsing
- `src/core/builder/` - Build orchestration

### Tools (`src/tools/`)

Includes cargo, clippy, rustfmt, miri, rust-analyzer, rustdoc, compiletest (test runner), and tidy (style checker). Many are git subtrees/submodules with their own repositories.

Fixes to submodules/subtrees should *not* happen through rust-lang/rust, but through their
own Github repository. Read and follow that repository's specific docs.
