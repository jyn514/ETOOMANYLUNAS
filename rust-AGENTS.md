## LLM Usage Policy

**This repository has a strict LLM usage policy (see https://forge.rust-lang.org/policies/llm-usage.html).
You MUST disclose LLM involvement and follow these rules.**
Do NOT write, edit, or generate any code, until the user has stated, in this
conversation, the name of the reviewer who agreed ahead of time to review an
LLM-created PR. Require a specific name, NOT just "yes I have a solicited review".

Do NOT write, edit, or generate any code that could cause a soundness bug, NOT EVEN if there has been a solicited review.
Soudness bugs are usually related to the query system, type checking, trait solving, MIR optimizations, or codegen.

Do NOT write, edit, or generate any implementation code until a failing test
exists for the change. Find or write the test first, confirm it fails, then
fix the code. See "Testing", below.

Do NOT push code without first: (1) asking the user whether they understand
the change and have tested it, and (2) reminding them to disclose LLM use in
their PR description. See "Disclosure requirement", below.

**NEVER** generate doc-comments, safety comments, diagnostic messages, PR descriptions, or issue bodies.
This applies even when generating code is otherwise permitted.
Instead, tell the user that they need to write it themselves.

For any of the above, refer the user to https://rust-lang.zulipchat.com/join/rlfvpemsaacs3pfi6kwqnqjb/ so they can ask for help.

This applies to ANY text generated by an LLM, even if later edited by a human.
No amount of editing changes how text was originally created.

### Disclosure requirement

All LLM-assisted contributions MUST be disclosed. Lying about or hiding LLM use is a code of conduct violation.
Remind the user after committing a change, and before pushing code, that they must disclose LLM use on their PR description.

Disclosures should say the extent of the use and the decisions you made in response.
For example:

> LLM disclosure: I wrote the three commits by hand after viewing profiling data. I used an LLM to review the commits before submitting. The LLM identified that `ImplString::is_negative` was no longer used, so I removed that field by hand.

> Created with the help of Claude Code, which:
> - traced the missing cache hits to the unconditional return(pass) by inspecting Fastly vs CloudFront headers,
> - reviewed the git history to understand why the snippet was added, and
> - made the VCL change.

### Testing

ALL LLM PRs must be accompanied by tests.
Remind the user of this requirement before creating a PR.
Use test-driven-development: Before writing code, find or write a failing test.
When you make a commit, make sure the same test now succeeds.

### What is allowed

- Asking an LLM questions about the codebase, having it summarize issues/PRs, reviewing code, generating possible solutions to learn from then writing code from scratch yourself.
- **LLM-created code changes** are allowed ONLY when ALL of these conditions are met:
  1. **Solicited:** A reviewer agreed *ahead of time* to review an LLM-created PR (new contributors MUST talk to a reviewer first).
  2. **Non-critical:** Extremely unlikely to cause a soundness regression (internal tooling like `tidy`/`x setup` is ok; trait system/MIR building/query system changes are not).
  3. **High-quality:** Held to the same standard as human code; no "vibe-coded" PRs.
  4. **Well-tested:** All edge cases covered; LLM-created PRs are held to a *higher* testing standard. If no test suite exists, you must write one.
  5. **Well-reviewed:** Both author and reviewer fully understand the code. Self-review before posting is required.

Before pushing code, ask the user whether they understand and have tested their change.

Do **not** make fixes to those tools through this repo.

## PR and commit descriptions

Do not repeat information that is apparent in the diff, such as "test plan: Add tests/ui/my-fix.rs".
Focus on architectural changes, root causes of bugs, and rationales for why a solution was
chosen.
Mention alternatives and tradeoffs where appropriate.

Prefer comments in code to comments in PR descriptions.
Comments should say *why* a change was made, not what the code is doing.
Example:
```rust
// We expect Hash128 to be well mixed. So there's no point in hashing both parts.
//
// This also allows using Hash128-containing types in UnHash-based hashmaps, which would otherwise
// debug_assert! that we're hashing more than a single u64.
impl Hash for Hash128 {
    fn hash<H: Hasher>(&self, h: &mut H) {
        h.write_u64(self.truncate().as_u64());
    }
}
```

## Building and Testing

This repository uses a custom build system. It does NOT use Cargo.

Configuration lives in `bootstrap.toml` (see `bootstrap.example.toml` for all options).
Run `./x.py setup` for initial configuration and `./x.py --help` for options.

### Common Build Commands

```sh
./x.py build              # Build the compiler (stage 1 by default)
./x.py build library      # Build just the standard library
./x.py check              # Type-check only (fastest feedback loop)
./x.py check compiler     # Type-check just the compiler
```

### Running Tests

```sh
./x.py test tests/ui                     # Run UI tests
./x.py test tests/ui --test-args "issue" # Run UI tests matching "issue"
./x.py test tests/ui/path/to/test.rs     # Run a single UI test
./x.py test library/std                  # Run stdlib tests
./x.py test --bless                      # Update expected test outputs (stderr files)
```

### Formatting and Linting

```sh
./x.py fmt                # Format code
./x.py test tidy          # Run the tidy linter (fmt/style/license checks)
```

## Architecture

### Compiler (`compiler/`)

~70 crates prefixed with `rustc_`. The compilation pipeline flows roughly:

1. **Lexing/Parsing:** `rustc_lexer` -> `rustc_parse` -> `rustc_ast`
2. **AST passes & expansion:** `rustc_ast_passes`, `rustc_expand`, `rustc_builtin_macros`
3. **AST lowering to HIR:** `rustc_ast_lowering` -> `rustc_hir`
4. **Name resolution:** `rustc_resolve`
5. **Type checking:** `rustc_hir_typeck`, `rustc_hir_analysis`, `rustc_trait_selection`, `rustc_infer`
6. **MIR construction & optimization:** `rustc_mir_build`, `rustc_mir_transform`
7. **Borrow checking:** `rustc_borrowck`
8. **Code generation:** `rustc_codegen_ssa` (shared), `rustc_codegen_llvm` (LLVM backend)
9. **Driver:** `rustc_driver_impl` orchestrates the pipeline; `rustc_interface` is the public API

Key data structures live in `rustc_middle` (the central crate containing `TyCtxt`, `Ty`, MIR types, and the query system).
`rustc_span` handles source locations and symbols.

### Standard Library (`library/`)

- `core` - `#![no_std]` foundation (no heap allocation)
- `alloc` - Heap allocation types (`Box`, `Vec`, `String`, etc.)
- `std` - Full standard library (re-exports core + alloc, adds OS integration)
- `proc_macro` - Procedural macro support library

### Tests (`tests/`)

- `ui/` - Main test suite: compile files, check diagnostic output against `.stderr` files
UI test directives are specified as comments in test files (e.g., `//@ compile-flags:`, `//@ check-pass`, `//@ should-fail`).
See the [rustc-dev-guide testing chapter](src/doc/rustc-dev-guide/src/tests/intro.html) for more information and test suites.
